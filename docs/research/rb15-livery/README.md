# RB15 livery recon — milestone 1 (two RB15s, two liveries)

Date: 2026-09-18. Scope: read-only inspection of RB15 F1 Car Mod Demo v10 (Nexus 31543, `fable5.archive`) plus a
separate, dependency-based test add-on. **Nothing in the RB15's own files was modified** (checkpoint-05 deployment
record shows 4 new files, 0 overwrites). Physics, drivetrain, meshes, ERS, MT compatibility and NCM race logic are
untouched; the add-on only adds an *appearance* and a *material*.

Status: **MILESTONE 1 PASSED (2026-09-18)** — stock Red Bull RB15 and the green "NCM TEST" RB15 spawned side by side
on the highway with all 13 RB15 files hash-verified unchanged. The ArchiveXL mesh patch (new appearance + material
merged into `rb15_body.mesh`) works. See "Adding real liveries" for the production workflow.

## 2. UV mapping — usable as-is

Yes. UV0 of every `rb15_ext` chunk lies in 0..1 with no overlaps between parts, laid out as a classic
game-livery atlas (the stock Red Bull art is literally painted on it). No re-unwrap needed.

## 3. UV template (generated)

`wolvenkit-projects/ncm_rb15_liveries/uv-templates/`

- `rb15_ext_uv_template_4096.png` — transparent 4096² UV wireframe (drop in as a top layer in GIMP/Photoshop).
- `rb15_ext_uv_wireframe.png` — wireframe over the stock art, chunk numbers labelled.
- `rb15_ext_uv_regions_4096.png` / `_2048.jpg` — colour-coded regions (front wing, rear wing, nose, sidepod L/R,
  engine cover, cockpit/halo, floor, mirrors, rear/diffuser). Region split is a heuristic from 3D bounding boxes; the
  big islands are reliable, the fine sidepod/engine-cover border is approximate.

Generated by decoding the mesh's vertex buffer directly (`tools/rb15_uv.py`, `tools/rb15_template.py`); the
WolvenKit CLI glTF exporter refused to run without a materials depot, so the scripts don't need it.

Orientation notes (game space, +Y = nose): front wing = chunk 31 (top-left of atlas: "Red Bull Racing" endplate +
striped planes), rear wing = chunk 18 (top-right: big "Red Bull" main plane + yellow endplates), rear-wing "23"
numbers top-right, nose top-centre strip ("Aston Martin" mirrored text), sidepods right-centre, engine cover/shark fin
centre-left, floor bottom-left.

## 5–6. Supporting multiple liveries simultaneously — chosen method

**Appearance + material variants added to the author's assets via ArchiveXL resource patches, selected per
spawn by `appearanceName`.** Not global texture replacement, not mesh copies.

Why not the alternatives:
- Overriding `2019_f1_red_bull_rb15_ext_23.xbm` by path → every RB15 gets the same skin, and it overrides the author's file. Rejected.
- Copying `rb15_body.mesh` with new materials → redistributes the author's geometry. Rejected.
- Runtime material swapping via CET/Codeware → no supported API to retarget a mesh component's material after spawn; hacks (toggle `body_01`, add a second mesh component) risk collision/skinning. Rejected for now.
- Game "Crystal Coat"/vehicleVisualCustomization → only works on `vehicle_paint` materials with colour params; the RB15 uses `metal_base` + albedo texture. Not applicable.

Chain per livery `X` (all files live in **our** archive, `ncm_rb15_liveries.archive`, which depends on the RB15):

1. `ncm\rb15_liveries\textures\rb15_ext_X.xbm` — the artwork.
2. `ncm\rb15_liveries\meshes\rb15_body_liveries.mesh` — **geometry-free mesh patch**. Contains only: mesh appearance
   `X` (chunk→material list copied from `default`, with `rb15_ext` → `rb15_ext_X`) and local material `rb15_ext_X`
   (metal_base, `BaseColor` = our xbm). ArchiveXL merges it into `fable5\rb15\meshes\rb15_body.mesh` at load
   (`resource.patch` in the `.xl`). Unpatched chunks keep the author's materials by name.
3. `ncm\rb15_liveries\rb15_liveries.app` — our own `.app` with appearance `X` = clone of `player_01` where `body_01`
   and the proxy component use `meshAppearance X`. (This clones the *component layout* — positions, lights, donor mesh
   references — as data; it contains none of the author's meshes/textures/scripts. Flagged as a judgment call; if the
   author objects, this is the file to negotiate. `.app` patches can't express "same as player_01 but one field", so
   there is no smaller form.)
4. `ncm\rb15_liveries\rb15_ent_patch.ent` — **.ent patch** adding one appearance entry to `fable5\rb15\rb15.ent`:
   `name X, appearanceName X, appearanceResource ncm\rb15_liveries\rb15_liveries.app`.
5. `r6\tweaks\ncm_rb15_liveries.yaml` — `Vehicle.v_sport1_rb15_f1_X: { $base: Vehicle.v_sport1_rb15_f1, appearanceName: X }`.
   Inherits physics/drivetrain/entity template; not appended to `Vehicle.vehicle_list` (AI use only).

Test build also carries `rb15_ncm_fallback.ent` (+ record `..._ncm_test_fb`) = full copy of `rb15.ent` with the extra
appearance entry, used **only** to distinguish "mesh patch failed" from ".ent patch failed". **Local test only — it
contains the author's compiled entity data and must not ship.** Remove after the test.

## 7. What NCM must specify per rival

NCM already spawns rivals through Codeware `DynamicEntitySystem` (`ai_vehicles.lua` `buildDynamicEntitySpec`) with
`spec.recordID` and an optional `spec.appearanceName` — but every caller (`spawnVehicleEntity` at ~5314/5395/5887)
passes `appearance = nil`. Two equivalent options once the test passes:

- **Option A (preferred):** keep `Vehicle.v_sport1_rb15_f1` as the record and pass `appearanceName = "<livery>"`
  per driver. One record, N liveries. Needs: a `livery` field on the driver/slot (roster or vehicle_pool profile) and
  `spawnVehicleEntity(slot.vehRecord, entPath, pos, heading, slot.livery)`. Hotkey D in the tester checks that this
  spawn-time override works.
- **Option B:** one derived record per livery (`Vehicle.v_sport1_rb15_f1_<livery>`) and put that record in the pool.
  Zero NCM code change, but N records. Hotkey B tests this.

Player's own RB15 stays stock `player_01` in both cases.

## 8. Redistribution / dependency

The add-on ships only: our texture(s), the geometry-free mesh patch, our `.app`, the `.ent` patch, `.xl`, TweakXL
yaml. It references the author's meshes/textures by path and requires the original RB15 installed (ArchiveXL
patches simply no-op with a warning if the target is missing). See the `.app` caveat in §5–6 step 3.

### What the test decides (fill in)

| Hotkey | Result | Meaning |
|---|---|---|
| B (patch route) | ☐ test livery / ☐ stock / ☐ missing body | mesh patch + .ent patch both work / .ent patch didn't add the entry / mesh patch or material name resolution failed |

## Art pipeline (what you edit in GIMP/Photoshop, and how it becomes a livery)

**Source art you edit:** a 4096×4096 RGB PNG. Start from either
- `wolvenkit-projects/ncm_rb15_liveries/source/ncm/rb15_liveries/textures/rb15_ext_ncm_test.png` (flat test), or
- the stock art extracted to the scratchpad (`2019_f1_red_bull_rb15_ext_23.png`, re-extract with
  `WolvenKit.CLI uncook fable5.archive -r "\.xbm$" --uext png`) — useful as a reference layer, **do not** ship it.

Layers: your paint on the bottom; `uv-templates/rb15_ext_uv_template_4096.png` on top (wireframe, transparent) and/or
`rb15_ext_uv_regions_4096.png` at ~40 % opacity for part names. Hide the template layers before export. Alpha is
ignored by `metal_base` here, so export opaque RGB. Text on the atlas appears mirrored on some panels — that is the
mesh's UV orientation, check in-game; the stock art shows which islands are mirrored.

**Export:** PNG, 4096×4096, 8-bit, sRGB, no template layers, file name `rb15_ext_<livery>.png`.

**Convert to `.xbm` (WolvenKit CLI 8.20, `tools/WolvenKit.Console-8.20.0`):**
```
# 1) plain import (produces TCM_None / linear — not what we want, but gives us a header to edit)
WolvenKit.CLI.exe import rb15_ext_<livery>.png -o <dir>
# 2) serialize, set setup.compression=TCM_QualityColor, setup.isGamma=1, deserialize back
WolvenKit.CLI.exe convert s <dir>\rb15_ext_<livery>.xbm   -> edit the .json -> WolvenKit.CLI.exe convert d <dir>\rb15_ext_<livery>.xbm.json
# 3) re-import keeping the header (compresses to BC7 with sRGB + mips)
WolvenKit.CLI.exe import rb15_ext_<livery>.png -o <dir> --keep
```
(Or in the WolvenKit GUI Import Tool: Compression = QualityColor, Is Gamma = on, Generate mipmaps = on.) Verify with
`convert s`: `textureDataSize` should be 22,369,648 like the original.

**Register the livery:** run `tools/build_mesh_patch.py` and `tools/build_app_ent.py` (currently hard-coded to
`ncm_test`; parameterise to take a list of livery names — each adds one mesh appearance + material, one `.app`
appearance, one `.ent` appearance entry), add a `Vehicle.v_sport1_rb15_f1_<livery>` record (or just use the appearance
name with NCM Option A), then:
```
WolvenKit.CLI.exe convert d <the three .json files>
WolvenKit.CLI.exe pack <folder containing ncm\...> -o <out>     -> ncm_rb15_liveries.archive
```
Copy `ncm_rb15_liveries.archive` + `.xl` to `archive/pc/mod/`, the yaml to `r6/tweaks/`. No RB15 file is touched.

## Adding real liveries (production workflow)

1. Paint at 4096x4096 in GIMP/Photoshop using `uv-templates/rb15_ext_uv_template_4096.png` (and the regions map) as
   top layers. Keep the layered file; export a flattened **8-bit RGB PNG, sRGB, opaque** named
   `rb15_ext_<name>.png` (`<name>` = lowercase letters/digits/underscore).
2. Drop it in `wolvenkit-projects/ncm_rb15_liveries/liveries/`.
3. `python wolvenkit-projects/ncm_rb15_liveries/tools/build_liveries.py --deploy` (game closed). Add `--with-test` to
   keep the green test livery. The script extracts the RB15 references read-only, converts every PNG to BC7/sRGB xbm,
   regenerates the mesh patch, `.app`, `.ent` patch, `.xl`, TweakXL yaml and a `ncm_rb15_liveries.manifest.json`
   listing `appearance_names` / `records`, packs `ncm_rb15_liveries.archive`, writes `out/payload` + a zip, and
   (with `--deploy`) copies only our files into the game. Removing a PNG removes that livery on the next build.
4. In game: appearance name = `<name>`; record = `Vehicle.v_sport1_rb15_f1_<name>`. Spawn either way.

Typical build time: ~60-90 s per livery (WolvenKit CLI startup per step + 4096² BC7 encode).

Verified 2026-09-18: a two-livery build (`ncm_test` + `demo_orange`) packs and round-trips cleanly and is deployed.
Implementation note for anyone editing the script: cloned appearances must have their `HandleId`/`HandleRefId`
(and `BufferId`) renumbered with one consistent mapping per clone — WolvenKit rejects duplicate handles across
appearances and dangling `HandleRefId` references (`clone_unique()` does this).

Test hotkeys (CET mod `NCM_RB15_LiveryTest`): *spawn STOCK*, *spawn NEXT livery (stock record + appearanceName)*,
*spawn NEXT livery (per-livery record)*, *despawn all*. The two NEXT variants correspond to NCM options A and B.

## Badge / decal plates (added 2026-09-18, optional per livery)

Same mechanism, second material slot. The RB15's floating plate geometry (chunks 16/22/24, material `rb15_badges`,
1024² decal sheet: Red Bull Racing logo plate, HIGH VOLTAGE triangle, "E" roundel, fastener caps) can be repainted
per livery by adding `liveries/rb15_badges_<name>.png`. `build_liveries.py` then clones the stock `rb15_badges`
material as `rb15_badges_<name>` in the patch mesh and rewrites only that livery's `chunkMaterials`. Resolution
order: own sheet → `liveries/rb15_badges_default.png` → stock (unpatched name, nothing changes). Recorded in the
manifest under `badges`. Verified: two-livery build with `ncm_test`=stock, `demo_orange`=own packs and round-trips;
deployed 2026-09-18 18:45. Artist-kit additions: `rb15_badges_uv_template_1024.png`, regions map, probe sheet.
Not extended to `rb15_misc` / `rb15_cab` / wheels (out of scope for now; same recipe would apply).

## Erratum 2026-09-18 (evening): UV templates were vertically flipped

The in-game probe livery showed rear-wing endplate cells G8/H5 and front-wing endplate G1 where the decoded UVs
placed rows A/B. Cause: the game samples V flipped relative to the WolvenKit mesh-JSON UV dump (the atlas is
almost top/bottom symmetric, so the wireframe "matched" the stock art either way). Fix: `tools/rb15_uv.py` now
applies `v = 1 - v`; all templates, region/mirror maps and badge templates were regenerated, and a software
renderer (`tools/rb15_render.py`) that textures the decoded mesh reproduces both the probe screenshots and the
stock Red Bull livery exactly (renders in `artist-kit/reference-renders/`). Established facts:
+X = car's right; left-side panels read as painted; right-side panels are rotated 180° (the stock art paints them
upside-down); only ~1 % of triangles are truly mirrored (trim). The `kiroshi_draft` livery was painted on the
flipped template and needs a vertical flip + text redo. Kit and public repo (commit df526a8) updated.
